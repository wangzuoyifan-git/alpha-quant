## 一、设计原则与层次化架构约束

### 1.1 模块化与分层隔离

- 系统整体按数据层、策略层、引擎层、Agent 层、应用层分层（具体布局见 `docs/project.md` 3.1 节）
- 各层责任明确，通过明确接口和数据契约解耦
- 数据域严格物理隔离，支持单域独立更新、迁移和扩展

**Agent 层内部分层决策结构（2026-06-12 重定位）：**

Agent 层实现三层决策架构（L1 宏观 → L2 行业 → L3 个股），系统定位**多周期配置+择时**，遵循以下约束：

1. **约束传递原则**：上层输出约束上下文（decision_context），下层在约束内决策
   - L1 宏观层输出 regime / risk_mode / max_position / **allocation（配置仓:交易仓资金分配）**
   - L2 行业层输出 allowed_industries / industry_detail / **allowed_styles / industry_horizon_map**
   - L3 个股层在约束内产出两类输出：交易仓信号（BUY）/ 配置仓候选（WATCH）

2. **约束前置原则**：下层动作空间必须在进入前收窄，不能"扫完再过滤"
   - 错误模式：全市场扫描 → 过滤行业
   - 正确模式：行业筛选 → 只扫行业池内标的

3. **决策可回流原则**：每层决策持久化，支持下次运行时绩效反馈
   - decision_log 记录每层输入输出（含 node_audit，阶段三已实现）
   - 阶段五实现"收益回填 → 参数自优化（L-A）→ 经验记忆（L-B）"闭环

4. **融合架构原则**：规则负责广度（全市场扫描），LLM 负责深度（约束语义解读+候选深度分析）
   - 规则角色：证据/特征提取器（把数据加工成结构化"事实"）
   - LLM 角色：综合分析师（融合结构化证据+非结构化信息做加权推理）
   - autonomy_level 总闸门控制 LLM 方案的执行权（详见 docs/agent.md）

详细设计见 `docs/agent.md` 第五（新）章、`docs/requirements.md` 第八章。

### 1.2 接口与封装规范

- 核心功能必须以 Tool 层形式封装，返回结构化数据（dict），不依赖命令行或日志解析
- Tool 层函数具备幂等性和独立性，方便单元和集成测试
- Agent 调用接口设计要考虑异步、批量和异常恢复能力

### 1.3 配置驱动与可动态调优

- 所有参数固定化改为配置驱动，配置集中管理（`config/settings.py`）
- 风控参数、信号筛选规则、并发数等均支持动态调整
- 支持基于运行时反馈修改配置，支持 Agent 层调优

### 1.4 状态管理与运行数据持久化

- 关键运行状态和结果全量持久化，支持断点恢复和审计
- 状态持久化结构格式约定统一，方便 Orchestrator 调度
- 日志级别细化，错误、警告和正常信息明晰

## 二、性能设计指标与运行监控

### 2.1 关键性能指标（KPI）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 全市场日线扫描时长 | ≤ 120 秒 | 含多线程并发执行 |
| 单标的查询响应时长 | ≤ 100 ms | 关键实时接口 |
| 数据增量更新时长 | ≤ 10 分钟 | 包含断点续传 |
| 扫描到推送端到端延迟 | ≤ 60 秒 | 多渠道推送策略信号 |
| 日常系统异常率 | < 0.1% | 触发自动告警 |

### 2.2 性能指标配置化与多环境适应

- 所有指标阈值通过配置驱动，默认基于当前本机环境设置
- 支持为不同硬件、部署环境定义不同阈值
- 允许动态调整，支持在运维看板查看历史趋势指标

### 2.3 监控与告警设计

- 监控 CPU / 内存 / I/O 使用率与关键业务流程耗时
- 数据覆盖率与异常告警触发频率
- 推送成功率及失败重试率
- 日志集中管理与自动异常告警

### 2.4 性能压测与容量规划

- 定期对关键模块做压力测试，验证系统承载能力
- 按不同场景模拟收盘后的更新及扫描峰值负载
- 评估性能波动原因，制定针对性优化措施

## 三、可靠性设计原则

### 3.1 原子写入与断点续传

- 确保批量数据导入原子性，防止中断后数据损坏
- 支持任务断点续传，避免重复作业和资源浪费

**Agent 工作流断点续跑（2026-06-11 阶段三新增）：**

分层决策链路变长（L1→L2→L3→风控→订单），全市场扫描耗时长，中断后整轮重来代价大。
工作流层基于 LangGraph Checkpoint 实现断点续跑（对应 requirements.md OB-R4）：

- `build_workflow(checkpointer=...)` 编译时注入 checkpointer，LangGraph 在每个节点后
  自动落盘状态快照
- 持久化优先 SQLite（`data/cache/checkpoints/workflow.sqlite`），依赖缺失时降级
  内存 checkpoint（保证逻辑可用，仅不跨进程）
- 一次运行以 `thread_id=<date>` 标识，崩溃后相同 thread_id 重跑从最后成功节点恢复，
  已完成节点（含已完成的扫描）不重复执行
- 与数据层「断点续传」是两个层次：数据层保证单域下载原子性，工作流层保证多节点决策链路可恢复

### 3.2 多源交叉验证

- 关键行情与财务数据至少双源采集
- 两源数据偏差过大触发自动告警，保障精准性

### 3.3 熔断与异常告警

- 基于 VIX、指数大幅波动等事件驱动熔断
- 持续监控异常，支持人工干预恢复
- 多级日志，提升异常排查效率

### 3.4 异常处理与灾难恢复

- 关键异常自动记录，支持审计与问题回放
- 定期备份重要数据，保障快速恢复
- 支持日志分级，区分紧急程度

## 四、Agent 层设计边界与接口规范

### 4.1 设计边界

- Agent 层为系统任务调度及决策逻辑层，基于 Tool 层
- 多 Agent 角色明确（数据、策略、风控/交易），详细架构见 `docs/agent.md` 第二章
- 支持异步并行执行，统一状态管理和异常恢复

### 4.2 调用接口规范

- Tool 接口均返回结构化字典，包含 `success`、`data`、`error` 字段
- 支持批量操作及超时控制
- 接口严格定义参数类型和返回结果格式

### 4.3 分层决策接口契约（2026-06-11 新增）

**decision_context 数据契约**：贯穿 L1→L2→L3 的全局约束对象

```python
decision_context = {
    "regime": str,                       # L1: 宏观状态
    "risk_mode": str,                    # L1: defensive/balanced/aggressive
    "max_position": float,               # L1: 总仓位上限
    "allowed_industries": list[str],     # L2: 行业池（阶段二填充）
    "industry_weights": dict[str, float],# L2: 行业权重（阶段二填充）
    "strategy_keys": list[str],          # L1/L2: 策略组合
    "timestamp": str,                    # 决策时间戳
}
```

**分层节点接口约束**：
- 每个决策节点接收 WorkflowState，读取上层写入的 decision_context
- 节点只能**收窄**约束，不能放宽（如 L2 不能扩大 L1 限定的仓位）
- 条件边路由函数必须有 default 分支（AC11），避免新增状态时流程卡死
- WorkflowState 新增字段必须 `total=False`（AC10），保证向后兼容

### 4.4 运行监控

- 采集 Agent 运行日志和调用链路
- 支持动态配置更新和实时权重调整
- 记录决策依据，支持审计追溯
- **分层决策日志**：decision_log_<date>.json 记录每层（L1/L2/L3）的输入输出和判定理由（对应 requirements.md OB-R1）
